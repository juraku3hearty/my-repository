## 1. Cyfonsの退会管理 ── 滞らせない仕組み

### 1-0. 問題の捉え直し

「退会リストを出す」が効かないのは、リストが **作業の依頼** にすぎないからである。
依頼は忘れられる。必要なのは次の3つで、**3が最も効く**。

1. 完了を自己申告で消さない（機械で検証する）
2. 未処理が時間とともに目立つ（エスカレーションする）
3. **止め忘れても損害が小さい構造にする**（根本解決）

### 1-1. 根本解決：価値の置き場所を変える

Cyfonsの停止が自動化できないなら、**Cyfonsに置くものを「止め忘れても痛くないもの」に限定する。**

| 置き場所 | 内容 | 退会時 |
|---|---|---|
| **Q&Aアプリ側**（止められる） | AI実務Q&A、新しい講座、解説PDF、相談窓口 | `status` で即時遮断 |
| **Cyfons側**（止めにくい） | お知らせ、過去講座のアーカイブ、会員規約 | 数日残っても損害は小さい |

これで、退会処理が1日遅れても失われる価値がほぼなくなる。
停止の自動化は「できたら嬉しい」程度に格下げでき、運用の緊張がなくなる。

### 1-2. 自動停止の手段（安全な順）

#### 案A：会員ページの前に「門番」を1枚置く ★第一候補

Cyfonsのコードもデータも **一切触らない。** `.htaccess` の `php_value auto_prepend_file` で、
Cyfons配下の全PHPの実行前に自作の `gate.php` を差し込む。

```
会員がCyfonsの会員ページを開く
   ↓ gate.php が先に動く
   ↓ Cyfonsのセッションから会員を特定
   ↓ Q&Aアプリの /api/status に問い合わせ（1秒キャッシュ）
status が active 以外 → 支払い案内ページを出して exit
```

| | 評価 |
|---|---|
| 安全性 | ◎ Cyfonsのデータを書き換えない。壊しても `.htaccess` の1行を消せば即復旧 |
| アップデート耐性 | ◎ Cyfons本体を改変しないので、更新で消えない |
| 即時性 | ◎ 完全自動・即時遮断 |
| **前提** | **2章の検証（セッションが読めるか）に成功すること** |
| 【要確認】 | レンタルサーバーで `auto_prepend_file` が使えるか。**【推測】** エックスサーバーは `.htaccess` での指定が可能と思われるが未確認 |

> **重要：** この案Aの前提は、2章のログイン連携の検証と **まったく同じ**。
> セッションが読めれば「署名付きリンク」と「退会の自動停止」が **同時に解決する**。
> 読めなければ、両方とも別の手段に落とす。検証が1回で2つの答えを出す。

#### 案B：CSVの再インポートでログインパスワードを無効化（半自動）

Cyfonsの公式機能の範囲内で確実に効く。**削除ではない** ので、データは残り復帰もできる。

```
全会員データダウンロード → 退会者のパスワード欄をランダム値に差し替え → 再インポート
```

- 【確認済】「全会員データダウンロード」→CSV編集→再インポートで、**ログインパスワードを修正できる**（出典：nssys.net/k33.php の検索要約）
- 退会者が何人たまっていても **1回のインポートでまとめて片付く**。作業時間が人数に比例しないので、滞りにくい
- 差分CSVはこちらで自動生成する。MAYUさんの操作は「落とす・入れる」の2クリック
- 完全自動化（HTTP POSTのスクリプト化）は、管理画面の仕様変更で壊れるため **採らない**

#### 案C：MySQL直接UPDATE

テーブル構造が未確認。アップデートで壊れる。**採用しない。**

### 1-3. 自動化できない場合の「滞らせない」仕組み

案Aが使えず案B（半自動）になった場合に備えて、以下を実装する。案Aが通っても保険として残す。

#### (1) 完了を機械で検証する

自己申告のチェックボックスでは消えないようにする。

```
毎朝 06:00
  Cyfonsの全会員CSVを取得（または前回インポート結果を照合）
  ↓
  status が suspended / cancelled の会員が、まだCyfonsに有効な状態で載っているか
  ↓
  載っていれば「未処理」として残り続ける。人が「やった」と言っても消えない
```

#### (2) 残日数に応じてエスカレーションする

| 未処理の経過 | 通知先 | 内容 |
|---|---|---|
| 当日 | MAYUさんにLINE | 「退会処理 1件」＋差分CSVを添付 |
| 2日目以降 | MAYUさんに毎朝LINE | 「**2日経過** 未処理1件」 |
| 7日目 | MAYUさん＋院長にLINE | 「7日経過。退会者がまだ会員サイトを見られます」 |
| 常時 | 管理画面の最上部 | 未処理件数を赤バッジで常時表示。0件になるまで消えない |

#### (3) 作業を溜めない設計

- 退会処理を **月次の棚卸しにしない。** 決済停止を検知したその日に1件ずつ通知する
- 1件あたり2クリックで終わる形にする（差分CSVはこちらで生成済み）
- **担当を1人に決める。** 複数人だと「誰かがやる」になり必ず滞る

### 1-4. 1章のまとめ

```
2章の検証に成功 → 案A（門番PHP）で完全自動 ＋ (1)(2)を保険として常設
2章の検証に失敗 → 案B（CSV半自動）＋ (1)(2)(3)をフル実装
いずれの場合も → 1-1（価値をQ&A側に寄せる）は必ず実施する
```

## 2. ログイン連携の実機検証手順

**この検証が終わるまで、署名付きリンク方式は確定扱いにしない。**

所要：30〜60分。Cyfonsの本番環境で行うが、**既存データは一切変更しない**（読み取りのみ）。

### 事前準備

1. **Cyfonsのフルバックアップ**（ファイル一式＋MySQLダンプ）を取る。検証自体は読み取りだけだが、順序として先に取る
2. **検証用の会員アカウント**を1つ作る（自分のメールアドレス）。**本番会員のデータは一切出力しない**
3. 検証用ファイルの置き場所に `.htaccess` でIP制限をかける

```apache
# /cyfons/_probe/.htaccess
Require ip 〈自宅や院のグローバルIP〉
```

> グローバルIPは「確認くん」等で調べる。固定IPでない場合は、検証中だけランダムな長いディレクトリ名（例 `_probe_8f3a2c91d4/`）にして、終わり次第ディレクトリごと削除する。

### 手順1：環境の確認

```php
<?php // _probe/step1.php
header('Content-Type: text/plain; charset=UTF-8');
echo "PHP           : " . PHP_VERSION . "\n";
echo "session_name  : " . session_name() . "\n";
echo "save_path     : " . ini_get('session.save_path') . "\n";
echo "auto_prepend  : " . (ini_get('auto_prepend_file') ?: '(未設定)') . "\n";
echo "cookie_path   : " . ini_get('session.cookie_path') . "\n";
```

**見るところ：** PHPのバージョン。`save_path` が書かれていれば、同じサーバー上の自作PHPから同じセッションを開ける見込みが高い。

### 手順2：ログイン状態でCookieを見る

ブラウザでCyfonsに**検証用アカウントでログイン**し、開発者ツール → Application → Cookies を開く。

記録するのは **Cookie名だけ**（値はメモしない）。

- `PHPSESSID` があるか
- Cyfons独自の名前のCookie（`cyfons_...` など）があるか
- 各Cookieの Path と Domain

### 手順3：セッションの中身を見る ★本丸

**ログインしたのと同じブラウザで** 次のファイルを開く。

```php
<?php // _probe/step2.php  ※検証後に必ず削除
header('Content-Type: text/plain; charset=UTF-8');

// 手順2でCyfons独自のセッション名が見つかった場合はここで合わせる
// session_name('見つかった名前');
session_start();

echo "session_id : " . (session_id() ?: '(なし)') . "\n\n";
echo "--- \$_SESSION のキーと型 ---\n";
foreach ($_SESSION as $k => $v) {
    printf("%-24s : %s\n", $k, is_scalar($v) ? gettype($v) : gettype($v).'('.count((array)$v).')');
}
echo "\n--- Cookie名のみ ---\n";
print_r(array_keys($_COOKIE));
```

**判定：**

| 結果 | 意味 | 進む先 |
|---|---|---|
| `$_SESSION` に会員ID・メールアドレスらしきキーがある | ◎ **成功。** 署名付きリンク（方式2）と門番PHP（案A）の両方が可能 | 手順5へ |
| `$_SESSION` は空だが `session_id` は取れる | セッション名かsave_pathが別。手順4へ | 手順4 |
| Cookieすら見えない | Path/Domainが違う。手順4へ | 手順4 |

> **注意：** このファイルは会員のセッション内容を表示する。**検証が終わったら必ず削除する。** 消し忘れは情報漏洩になる。

### 手順4：セッションが直接読めなかった場合

CyfonsはDBにログイン状態を持っている可能性がある。

```sql
-- phpMyAdmin 等で、テーブル名だけ眺める（中身は見ない）
SHOW TABLES;
-- session / login / token / member を含む名前があるか
```

- セッションテーブルがある → CookieのトークンでそのテーブルをJOINして会員を特定できる。**条件付きで成功**
- 無い → **方式2は不可。** 方式3（独立ログイン）に確定

### 手順5：署名付きリンクの疎通テスト

成功した場合のみ。`qa.php` を1枚置いて、Q&Aアプリ側（まだ認証は実装しないので、検証用の受け口だけ）に飛ばして、会員IDが正しく渡ることを確認する。

```php
<?php // qa.php（検証版。署名のみ確認し、ログインはまだ実装しない）
session_start();
$member = $_SESSION['〈手順3で見つかったキー〉'] ?? null;
if (!$member) { header('Location: /login'); exit; }

$secret = getenv('QA_LINK_SECRET');            // 環境変数。ソースに書かない
$payload = json_encode([
    'sub'   => (string)$member,
    'exp'   => time() + 60,                    // 60秒だけ有効
    'nonce' => bin2hex(random_bytes(16)),      // 使い捨て
], JSON_UNESCAPED_UNICODE);
$b64 = rtrim(strtr(base64_encode($payload), '+/', '-_'), '=');
$sig = rtrim(strtr(base64_encode(hash_hmac('sha256', $b64, $secret, true)), '+/', '-_'), '=');

header('Location: https://qa.example.com/enter?t=' . $b64 . '.' . $sig);
```

Flask側で確認すること：署名が合うか、`exp` 超過を弾くか、同じ `nonce` の2回目を弾くか。

### 検証後の後始末（必須）

1. `_probe/` ディレクトリを **ディレクトリごと削除**
2. `qa.php` は検証版を削除し、本実装時に作り直す
3. `QA_LINK_SECRET` を本番用に再発行する（検証中の値は使わない）

### 検証結果 → 方式の確定

| 検証結果 | 採用する連携方式 | 退会の停止 |
|---|---|---|
| 手順3で成功 | **方式2 署名付きリンク** | 案A 門番PHP（完全自動） |
| 手順4で条件付き成功 | **方式2**（DBから会員特定） | 案A（同上） |
| どちらも不可 | **方式3 独立ログイン**（メールにワンタイムリンク。パスワードは増えない） | 案B CSV半自動＋検知通知 |

> これは「AIが未確認情報を補わない仕組みにしてください」という先のご指示に対する構造的な答えで、

### 3-6. 障害対応の体制（費用ではなくリスク）

自院での試験運用のうちは「落ちたら直す」で足りる。

- 復旧目標（例：平日日中4時間以内）を会員規約に書くか
- 夜間・休日に落ちた場合、翌営業日対応で許容されるか
- バックアップからの復旧手順を、MAYUさん以外も実行できる形にするか

有人の24時間監視を外注すると月数万円規模になる（【推測】）。**自院運用の段階では不要。**
