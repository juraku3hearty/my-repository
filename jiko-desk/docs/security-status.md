## 1. 決済通知の真正性

| | 実装済み | 未対応 |

| 署名の検証 | — | **公式資料に署名の記載が無い。**【未確認】サポートに確認中。提供されるなら検証を足す |
| 送信元IPの制限 | 許可リスト（`54.95.223.30` / `54.168.57.171`）。拒否はログに残す | **検証環境では切っている**（`ENFORCE_SOURCE_IP=1` で有効化）。本番はnginx側でも二重に絞る |

## 2. 通知の重複・順序逆転

| | 実装済み | 未対応 |
|---|---|---|
| 重複 | `(gid, kind)` を主キーにして `INSERT OR IGNORE`。2回目以降は保存も処理もしない | — |
| 順序逆転（解約後） | `cancelled` は最終状態。あとから成功通知が来ても `active` に戻さない | — |
| 順序逆転（停止後） | **停止・解約後に届いた古い「リトライ中」通知で使える状態に戻さない。** 復帰は成功通知のときだけ | — |
| 期限の巻き戻り | `paid_through` は常に大きいほうを採る | — |
| 処理の順序 | `received_at` の昇順 | **通知に発生時刻が含まれない。** 受信順＝発生順とは限らないため、上の3つで守る |
| 取りこぼし | 申込時に `pending` を作り、30分来なければ警告（ER系はキックバックされない仕様のため） | **日次照合が未実装** |
| 再送 | — | **自動再送の有無が未確認。** 無い前提で日次照合を作る |

### 検証結果

```
停止後に古いリトライ通知が届く → suspended のまま（使えるようにならない）
そのあと成功通知が届く       → active に復帰
解約後に成功通知が届く       → cancelled のまま
同じ gid の通知を2回送る     → 1件だけ保存・1回だけ処理
```

## 3. ワンタイムログイン

| | 実装済み | 未対応 |
|---|---|---|
| トークンの保存 | **生の値を保存しない。** SHA-256のハッシュのみ | — |
| 有効期限 | 15分 | — |
| 使い捨て | 1回使うと無効。2回目は拒否し警告を記録 | — |
| 強度 | `secrets.token_urlsafe(32)`（256ビット） | — |
| URLからの漏洩 | **フラグメント（`#`）で渡す。** サーバーに送られないので、アクセスログにもRefererにも残らない。JSが読み取ってPOSTし、`history.replaceState` でURLからも消す | — |
| Referer経由の漏洩 | `Referrer-Policy: no-referrer` | — |
| **XSS** | Jinja2の自動エスケープ。トークンは `innerHTML` に入れず `fetch` のボディで送る。**CSP** で外部スクリプトと外部送信を禁止 | **`'unsafe-inline'` を許可している**（ログイン画面のインラインJSのため）。本番では外部ファイル化して `'unsafe-inline'` を外す |
| 列挙対策 | 会員の有無にかかわらず同じ画面を出す。解約済みには送らない | — |
| **レート制限** | 同一IPからの要求 10回/時、同一宛先へのメール **5通/時**、トークン試行 20回/10分（超過は429）。**トークン試行は「失敗した回数」だけを数える**ので、院内の共有IPから複数人が正しくログインしても打ち止めにならない | **IP単位のためプロキシ経由では回避されうる。** 本番ではnginx側でも制限する |
| 後片付け | 使用済み・期限切れは削除 | 定期実行が手動（`/admin/process-events`）。cron化が必要 |
| セッション | `httponly` Cookie（Flask既定） | **`Secure` 属性は本番で有効化**（現在HTTP） |

### 検証結果

```
ログインメールを8回要求 → 5通で打ち止め
存在しないトークンで25回試行 → 429 で遮断
<script>alert(1)</script> を検索・申込 → 会員画面でも管理画面でもエスケープされる
Referrer-Policy / X-Frame-Options / X-Content-Type-Options / CSP すべて付与
```
