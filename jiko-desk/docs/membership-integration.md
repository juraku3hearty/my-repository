### 1-2. 推測

- **【推測】** `acid`（自動課金番号）が会員1人＝1契約の識別子になる。これをQ&Aアプリ側の会員レコードに持たせれば、決済側と会員側を1対1で結べる。
- **【推測】** キックバックには「決済成功」だけでなく失敗・リトライ結果も飛ぶ。ただしイベント種別の網羅性は未確認。
- **【推測・要注意】** 第三者のGitHub Issue（knowledgelabo/robot_payment_ruby #12）に「ロボペイには参照APIがないため、アプリ側で決済結果を蓄積している」という記述がある。**状態をpullで取得するAPIが無い、または限定的な可能性がある。** ただし公式APIリファレンスが2026年3月に公開されており、現在は改善されている可能性が高い。

### 1-3. 状態ごとの取得可否（現時点の見込み）

| 状態 | 取得手段の見込み | 確度 |
|---|---|---|
| 入会（初回決済成功） | キックバック | 高 |
| 決済成功（毎月） | キックバック | 高 |
| 決済失敗 | キックバック | 中（要確認） |
| 再決済（リトライ）の結果 | キックバック | 中（要確認） |
| 解約 | 自動課金停止APIを**こちらから叩く**ので自明。顧客都合の解約が管理画面で行われた場合の通知は要確認 | 中 |
| 利用期限 | 決済日から1か月として**自前で計算して持つ**のが確実 | — |

> 設計上の結論：**利用期限を相手システムに問い合わせない。** 最後に成功した決済日＋1か月＋猶予を自前のDBに `paid_through` として持つ。これなら参照APIの有無に依存しない。

## 2. 利用可能な通知・取得方法

3系統を**併用**する。どれか1つに依存しない。

| | 方法 | 役割 | 頻度 |
|---|---|---|---|
| A | 結果通知URL（キックバック） | 主系。即時に会員状態を更新 | 都度 |
| B | WEB API（自動課金停止など） | 制御系。退会時にこちらから叩く | 都度 |
| C | 管理画面のCSVダウンロード／一覧API | **照合系。** 日次でローカルDBと突き合わせ、取りこぼしを直す | 1日1回 |

Cが保険になるので、Aの通知が1件落ちても翌日には自動で復旧する。これが6章の答えでもある。

## 3. Cyfonsの会員登録・利用停止の自動化

### 3-1. 確認できたこと

| 事項 | 内容 | 出典 |
|---|---|---|
| 公開API | **見つからない。** 公式のAPI・外部連携仕様は確認できなかった | 各種レビュー記事 |
| 会員一括登録 | 管理画面で「名・姓・メールアドレス」をタブ区切りで貼り付け、またはCSVインポート | nssys.net/k32.php（検索要約） |
| メールのみ登録 | メールアドレスだけでも登録可。パスワードはシステムが自動発行 | 同上 |
| 会員情報修正 | 「全会員データダウンロード」→CSV編集→再インポートで、**ログインパスワード・登録日も修正できる** | nssys.net/k33.php（検索要約） |
| 登録フォーム | Cyfonsが自動生成。パスワードで保護でき、購入者だけが登録できる | nssys.net/k14.php（検索要約） |
| 削除 | 管理画面の会員管理から手動削除 | homeworkers.jp |
| 一時停止 | **専用機能は確認できなかった。** 削除で代替している運用例のみ | 同上 |
| DB | インストール1つにつきMySQLデータベース1つ | effibop.com ほか |

### 3-2. 結論

```
入口（登録）: 自動化できる見込みが高い
  → ROBOT PAYMENTの決済完了メールに、パスワード保護された登録フォームURLを載せる
  → 会員が自分で登録。Cyfons側の手作業ゼロ

出口（退会・停止）: 自動化する公開手段がない
  → 管理画面からの手動削除が唯一の確実な手段
```

**【推測】** MySQLを直接UPDATEすれば停止できる可能性はあるが、テーブル構造が未確認であり、Cyfonsのアップデートで壊れる。**推奨しない。**

> 2026-10-12 追記：「退会リストを出して手動で消す」では、従来からある *手動処理が滞る* 問題が解決しない。
> 恒久的な停止手段と、滞りを構造的に防ぐ仕組みを `docs/membership-verification.md` 1章で再設計した。

### 3-3. ここから導かれる最重要の設計判断

> **会員資格の正本（source of truth）をCyfonsに置かない。**

Cyfonsは出口を自動で閉められない。閉められない場所を正本にすると、退会処理が常に手作業に縛られる。
正本はQ&Aアプリ側のDBに置き、Cyfonsは「講座・お知らせを置く表示の場所」として使う。

## 4. Q&Aアプリと会員資格を共通管理する最も簡単な方法

### 4-1. 構成

```
ROBOT PAYMENT（決済の真実）
      │ キックバック（即時）＋ 日次CSV照合（保険）
      ▼
Q&Aアプリ members テーブル（会員資格の正本）  ← ここだけを見れば資格が分かる
      │
      ├─ Q&Aアプリ本体  … status を直接見て即座に遮断できる
      └─ Cyfons        … 登録は自動／停止は「退会リスト」を出して手動
```

### 4-2. membersテーブル（案）

| 列 | 内容 |
|---|---|
| `member_id` | 自前発番。**これが照合の軸**（例 `JK-000123`） |
| `email` | 連絡用。変わりうるので主キーにしない |
| `email_normalized` | 小文字化・前後空白除去。Cyfonsとの突き合わせ用 |
| `robotpay_acid` | 自動課金番号。決済側との結び目 |
| `status` | `active` / `grace` / `suspended` / `cancelled` |
| `paid_through` | 利用期限。**自前で計算** |
| `last_payment_at` / `last_failure_at` / `retry_count` | 督促の判断材料 |
| `cyfons_registered_at` / `cyfons_removed_at` | Cyfons側の反映状況 |

### 4-3. 「最も簡単」の中身

- 資格判定は `status` と `paid_through` の2列を見るだけ。Q&Aアプリは1行のWHERE句で済む
- Cyfonsのデータ構造に一切依存しない。将来Cyfonsをやめても `members` はそのまま使える
- 将来、別の会員サイトに展開するときも、この表の前にアダプタを1枚足すだけ（優先事項6を満たす）

## 5. 未払い時の自動督促とアクセス制御の連動

ROBOT PAYMENT側が7日ごと最大2回リトライする。**この14日間に権限を切ると誤遮断になる。** リトライの期間と猶予を一致させる。

| 経過 | きっかけ | status | Q&A | Cyfons | 通知 |
|---|---|---|---|---|---|
| 0日 | 決済失敗 | `grace` | **使える** | 使える | ROBOT PAYMENTがカード更新URLを自動送信 |
| 7日 | リトライ1 失敗 | `grace` | 使える（ログイン時に案内を表示） | 使える | こちらからLINE/メールで1回 |
| 14日 | リトライ2 失敗 | `grace` | 使える（警告を強める） | 使える | 最終案内 |
| 17日 | 猶予終了 | `suspended` | **遮断** | 退会リストに載る | 停止通知 |
| 任意 | 本人の退会申出 | `cancelled` | 遮断 | 退会リストに載る | — |

- `suspended` になっても **ROBOT PAYMENT側の課金は自動では止めない**。復帰の見込みがあるため。本人の退会申出か、こちらの判断で自動課金停止APIを叩く
- 遮断は「ログインさせない」ではなく「ログインはできるが検索結果を出さず、支払い案内を表示」にする。退会を減らす狙いと、誤遮断時の問い合わせが早く来る利点がある
- Cyfons側の停止は、**毎朝「退会・停止リスト」を自動生成してLINEに通知** し、管理画面で消す。退会は月に数件の想定なので1〜2分で終わる。完全自動化はCyfonsの仕様が確認できるまで保留

## 6. 通知失敗時の再処理と会員情報の照合

### 6-1. キックバック受け口の作り

1. **必ず即 200 を返す。** 受信したJSON/パラメータをそのまま `payment_events` に生で保存するだけにして、処理は後段のワーカーに回す。処理中に落ちても通知は成功扱いになり、相手側の再送に頼らない
2. **冪等性。** 決済IDを一意キーにする。同じ通知が2回来ても二重処理しない
3. **署名・送信元の検証。** キックバックに署名があるかは【要確認】。無い場合はURLに十分長いランダム文字列を含め、送信元IPを絞る
4. **失敗したイベントはキューに残して指数バックオフで再試行**（2分→8分→32分→2時間）。3回失敗したらLINE通知

### 6-2. 日次照合（これが本当の保険）

毎朝、ROBOT PAYMENTのCSV（または一覧API）を取得して `members` と突き合わせる。

```
決済側にあって members に無い   → 入会の取りこぼし。members を作って登録案内を送る
members にあって決済側に無い     → 解約の取りこぼし。status を見直す
paid_through と最終決済日が矛盾 → paid_through を決済側に合わせて直す
```

**通知が落ちても、翌朝には必ず正しい状態に収束する。** これがあるので、キックバックの信頼性に設計を預けなくて済む。

### 6-3. 照合キーの優先順位

```
1. robotpay_acid     … 変わらない。最優先
2. member_id         … 自前発番。変わらない
3. email_normalized  … 変わりうる。最後の手段。一致してもログに残して人が確認
```

メールアドレスを主キーにしない。会員がメールを変えた瞬間に別人になる。

## 7. 連携3方式の比較

評価：◎優 ○可 △難あり ✕不可

| | 方式1 iframe埋め込み | 方式2 署名付きリンク | 方式3 独立ログイン |
|---|---|---|---|
| 会員の動線 | Cyfons内の1ページに見える | Cyfonsのメニューから1クリックで移動 | Cyfonsとは別サイト |
| **実装負担** | △ iframe高さ調整＋トークン受け渡し | ○ 橋渡しPHP 1枚＋Flask側の検証 | ◎ Flaskだけで完結 |
| **セキュリティ** | △ X-Frame-Options緩和が必要。Cookieは `SameSite=None; Secure` 必須。クリックジャッキング対策を別途 | ◎ 短命（60秒）・1回限りの署名トークン。iframeを使わないのでCookie制約なし | ○ 標準的。ただしパスワード管理が1つ増える |
| **退会管理** | ○ Flask側で即遮断 | ◎ Flask側で即遮断。トークン発行時にも status を再確認するので二重に止まる | ◎ Flask側で即遮断 |
| **スマホ操作性** | ✕ **二重スクロール・高さ崩れ・キーボード出現時の表示崩れ。** 会員はほぼスマホなので致命的 | ◎ 普通のページ遷移。問題なし | ○ 問題ないがログインが2回 |
| **二度ログイン回避** | ◎ | ◎ | ✕ |
| **他サイトへの展開** | △ 埋め込み先ごとに調整 | ◎ 橋渡しの1枚を差し替えるだけ | ◎ |
| **Cyfons仕様への依存** | 中 | **中（セッション構造の確認が必要）** | ✕ なし |

### 第一候補：方式2（署名付きリンク）── **確定ではない。実機検証の結果待ち**

> 2026-10-12 追記：Cyfonsのログイン状態を自作PHPから読めるかが未検証のため、本方式は **保留**。
> 検証手順は `docs/membership-verification.md` を参照。検証が通るまで認証の実装は行わない。

**仕組み**

```
Cyfonsと同じサーバーに qa.php を1枚置く
  ↓ 会員がCyfonsにログイン済みの状態でクリック
qa.php が Cyfons のセッションからメールアドレス（または会員ID）を取得
  ↓ HMAC-SHA256 で署名したトークンを作る（有効60秒・1回限り・nonce付き）
https://qa.example.com/enter?token=... へ 302リダイレクト
  ↓ Flask側が署名を検証し、members の status を確認
status が active なら Q&Aのセッションを張る／そうでなければ支払い案内
```

**【要確認】** qa.php が Cyfons のログイン状態を読めるかどうか。同一サーバー・同一DBなのでセッションテーブルかCookieから辿れる見込みが高いが、**Cyfonsのセッション構造は未確認**。実機で確認が要る。

**代替案（Cyfonsのセッションが読めなかった場合）**
Cyfonsの会員向けページに、会員ごとの固定リンクを差し込みタグで出せるなら、`?mid=<会員ID>&sig=<署名>` を事前生成して埋め込む方式に切り替えられる。Cyfonsの差し込みタグ仕様が【要確認】。
それも不可なら、方式3（独立ログイン）に落とす。この場合も、Q&A側のログインを「メールアドレスにワンタイムリンクを送る」形にすればパスワードは増えない。

**方式1（iframe）を推さない理由**
スマホでの操作性が明確に落ちるため。優先事項1「会員が迷わずQ&Aを使えること」と真っ向から衝突する。見た目の統一のために使い勝手を落とす取引になる。

## 11. サブスクペイ キックバック受け口の仕様（2026-10-12 確定分）

公式ヘルプ「決済結果の通知方式（レスポンス・キックバック）について」（2026-06-05版）より。

### 確定した事実

| 事項 | 内容 |
|---|---|
| 通知方式の指定 | `rt=0` キックバック（サーバー間通信）／`rt=1` レスポンス（HTML・カンマ区切り） |
| **自動課金は選択の余地なし** | 2回目以降の決済結果は **仕様上キックバック固定**。「自動課金結果通知URL」の設定が必須 |
| URLは2本 | 初回・申込 → 決済結果通知URL／自動課金2回目以降 → 自動課金結果通知URL |
| リンク決済 | レスポンス方式は使えない。キックバック一択 |
| **送信元IP（本番）** | `54.95.223.30` / `54.168.57.171` |

### VPS側の受け口の設計（これで確定できる部分）

```nginx
# /webhook/subscpay/<長いランダム文字列>
location /webhook/subscpay/ {
    allow 54.95.223.30;
    allow 54.168.57.171;
    deny  all;
    proxy_pass http://127.0.0.1:8000;
}
```

- **URLのパスに十分長いランダム文字列を含める。** 署名の有無が未確認のため、
  IP制限とURLの秘匿を主な防御にする
- **拒否したアクセスは捨てずに記録する。** 2つのIPはAWS東京リージョンのもので、
  将来変更される可能性がある。黙って落とすと、IPが変わったときに通知が全部消えたことに気づけない
- 拒否が一定数を超えたらLINEに通知する

### それでも日次照合は外せない

送信元IPが分かっても、次は防げない。

- IPアドレスの変更（告知を見落とした場合）
- VPSの障害中に送られた通知
- こちら側の処理バグ

**毎朝のCSV照合で最終的に整合させる設計は維持する。**

### 残る未確認（サポートに確認する）

1. **決済失敗・リトライ失敗・解約のときもキックバックが飛ぶか**（成功時に飛ぶことは確定した）
2. キックバックの**パラメータ一覧**と、こちらの会員IDを載せられる自由項目の有無
3. **署名／認証の有無**
4. **通知エラー時の自動再送の有無と回数**
5. 契約・決済状態を後から取得できるAPIまたはCSV出力（日次照合に必要）
6. 自動課金停止APIの `aid` と認証情報の入手方法

## 12. キックバックの追加パラメータ（2026-10-12 確定分）

MAYUさん提供の「パラメータの追加依頼手順」より。**追加費用は不要。** 店舗IDと店舗名を添えて
お問い合わせフォームから依頼する。

### 設計に効く発見：**自由項目がない**

追加可能な一覧は、すべて **顧客の属性**（氏名・ふりがな・住所・電話・FAX・生年月日・
メール・カード情報・商品名・質問・配送先一式）である。
`free1` や `sendid` のような、**こちらが任意の値を入れられる項目が存在しない。**

> つまり **自動課金のキックバックに、こちらの会員IDを載せることはできない。**

### 紐付けの設計（これで確定）

```
初回申込時   こちら側で会員IDを発番 → 決済結果通知URLへのキックバックで acid を受け取る
             → members(member_id, robotpay_acid) として保存
2回目以降    自動課金結果通知URL に acid が載る → それで members を引く
```

**acid（自動課金番号）が唯一の安定キーになる。** 初回の1回だけ確実に捕まえればよい。

**【要確認】** 自動課金のキックバックの**既定の送信内容に acid が含まれるか。**
上の一覧は「既定で含まれないもの」の列挙なので、acid や金額・決済日時は既定で入ると思われる（【推測】）。
**ここが入っていないと紐付けが成立しないので、最優先で確認する。**

### 依頼するパラメータ：`em` と `nm` の2つだけ

| 依頼する | 理由 |
|---|---|
| `em` メールアドレス | **acid が取れなかった場合の予備の照合キー。** 日次照合でも使う |
| `nm` 名前 | 管理画面で誰か分かるように。退会リストの確認に要る |

### 依頼しないもの（重要）

| 依頼しない | 理由 |
|---|---|
| `cn4` カード下4桁、`ed` 有効期限、`ct` ブランド、`fn`/`ln` カード名義 | **カード情報を自分のサーバーに置かない。** 置いた瞬間に保護義務と漏洩時の被害が跳ね上がる。カード更新の案内はROBOT PAYMENT側が自動送信するので、こちらで持つ必要がない |
| `pst`/`adr`/`adrf` 住所、`pn`/`mpn` 電話、`fax`、`dob` 生年月日 | Q&Aアプリの運用に使わない。**使わない個人情報は受け取らない** |
| 配送先情報 一式（`p` で始まる9項目） | 物を送らないので不要 |
| `iid2` 商品名、`knw` 質問 | 単一プランのため不要 |

> **原則：使う予定のない個人情報は、無料でも受け取らない。**
> 受け取れば保存期間・アクセス制限・漏洩時の対応義務が発生する。
> 既に `docs/analytics-design.md` で質問文のマスキングと13か月保存を決めているので、
> ここでも同じ方針を通す。

### お問い合わせの文面（そのまま送れる形）

```
件名：キックバックパラメータの追加依頼

① 対象の店舗ID：〈管理画面に表示されている店舗IDを記入〉
② 店舗名　　　：〈契約時の店舗名を記入〉
③ 追加希望のパラメータ名：
   ・em（メールアドレス）
   ・nm（名前）

あわせて、以下についてもご教示ください。

1. 自動課金結果通知URLへのキックバックについて、既定の送信項目に
   自動課金番号（acid）が含まれるか。含まれない場合、契約と通知を
   紐付けるための識別子として何を利用すればよいか。
2. 決済が失敗した場合、および自動リトライが失敗した場合にも
   キックバックは送信されるか。
3. 解約（自動課金停止）が行われた場合にキックバックは送信されるか。
4. キックバックに署名や認証ヘッダは付与されるか。
5. 通知先がエラーを返した場合、自動で再送されるか。される場合の回数と間隔。
6. 契約・決済の状態を後から取得できるAPI、または管理画面からの
   CSV出力はあるか（日次の照合に利用したい）。
7. 自動課金停止APIを利用する際の店舗ID（aid）と認証情報の入手方法。
```

## 13. 「決済WebAPI」は有料オプション（2026-10-12 判明）

MAYUさん提供の「APIキーを発行・再発行する手順」より。

### 確定した事実

| 事項 | 内容 |
|---|---|
| APIキーの発行 | 有料オプション「決済WebAPI」の契約が必要。未契約だと設定画面にメニューが出ない |
| 認証方式が2つある | **HTTP API方式** と **REST API方式** で認証方法が異なる |
| **オプションが必要なのはREST API方式** | 原文：「REST API方式を使用される場合には、『決済WebAPI』のオプションが必要」 |
| 再発行は即座に停止 | 無効化した瞬間に旧キーが使えなくなる。復元不可。メンテナンス時間が要る |
| 月額 | **記載なし。【要確認】** |

### 設計への影響：オプションなしで成立するか

この設計で外部システムとやり取りするのは3か所。それぞれオプションが要るかを整理する。

| # | 用途 | APIキーが要るか | 見込み |
|---|---|---|---|
| 1 | **キックバックの受信**（主系） | **不要** | 向こうから送ってくるだけ。こちらは受けるポートを開けるのみ。**追加費用なしで動く** |
| 2 | **自動課金の停止**（退会時） | 方式による | `acsgate.aspx` に `aid`/`cmd`/`acid` を投げる形は **HTTP API方式**。原文の読み方では**オプション不要の可能性がある。【要確認】** |
| 3 | **日次照合のデータ取得** | 方式による | 管理画面からのCSVダウンロードなら不要。API経由なら要る |

> **キックバック（主系）が無料で動くのが大きい。** 会員資格の判定は1でまかなえる。

### オプションなしで組む案（第一案）

```
入会・毎月の決済   キックバック受信        → 追加費用なし
退会時の課金停止   管理画面から手動で停止   → 月に数件。1件1分
日次照合           管理画面からCSVを落とす  → 1日1回、数分。または当面は週1回
```

**退会処理は元々Cyfons側で手作業が残る見込みなので、課金停止もそこに合流させれば負担はほぼ増えない。**
（Cyfonsの会員削除をするついでに、管理画面で課金も止める）

### オプションありで組む案（第二案）

```
退会時の課金停止   自動課金停止APIを叩く   → 完全自動
日次照合           APIで取得               → 完全自動
```

手作業はゼロになるが、**月額が不明。** 金額次第で判断する。

### 判断の目安

| オプションの月額 | 判断 |
|---|---|
| 無料〜1,000円程度 | 第二案。手作業がゼロになる価値がある |
| 2,000〜3,000円程度 | 会員30人なら第一案、100人超なら第二案 |
| 5,000円以上 | 第一案。月数分の手作業のために払う額ではない |

### 運用上の注意（オプションを契約した場合）

- **APIキーの再発行は即座に旧キーを無効化する。** 連携は停止し、復元できない
- 再発行するときは**メンテナンス時間を取る**。深夜に行い、キー差し替え後に疎通確認する
- キーは `public_html` の外に置く（`docs/xserver-integration.md` 1-3と同じ）
- 漏洩時の手順を決めておく：無効化 → 新キー発行 → VPSの設定更新 → 疎通確認
