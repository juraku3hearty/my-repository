# ナレッジIDが再構築でずれる問題（2026-10-17 発見）

## 何が起きたか

ナレッジIDは `KB-<動画ID>-<連番>` で、**連番は動画内の出現順**で振られている。
動画 `1060102035` を再構築したとき、チャンクの切れ目が変わって連番が振り直され、
**同じIDが別の内容を指すようになった。**

| 院長に送ったシートのID | シートの内容 | 現在のDBで同じIDが指す内容 |
|---|---|---|
| KB-1060102035-013 | 通院慰謝料の計算方法と上限 | 一括対応の注意点と被害者請求 |
| KB-1060102035-016 | 月15日上限は総通院日数で判断されるか | 120万円を使い切る場合の施術費と慰謝料の目安 |
| KB-1060102035-017 | 慰謝料の計算方法と通院頻度の説明 | 保険会社から病院受診を指示された場合の対応 |

## 影響範囲

初回レビュー60件のうち

- **45件** IDと内容が一致（問題なし）
- **10件** IDがずれている。質問文と動画の秒数から新IDを特定できた
- **5件** 自動では特定できず、目で確認が必要

ずれているのは**すべて動画 1060102035**。ほかの動画のIDは動いていない。

第二弾96件は現在のDBから生成したので、**いま時点では正しい**。
ただし同じ再構築が起きれば同様にずれる。

対応づけの結果は `data/review-round1-remap.csv`（旧ID・新ID・一致度・院長の判定を併記）。

## なぜ放置できないか

公開承認は「`approval_state='承認済'` かつ `approved_version = answer_version`」で判定している。
IDがずれた状態で院長の判定をDBに書き戻すと、**別の項目に承認が付く。**
承認の仕組みそのものが意味をなさなくなる。

## 直し方

### 1. 連番をやめる（根本）

IDを出現順にしない。再構築しても動かない値にする。

- `KB-<動画ID>-<質問文のSHA-256 先頭8桁>` → 質問文を直すとIDも変わるので不可
- **採用: IDは一度振ったら固定する。** 再構築時は新チャンクを既存itemに
  （動画ID＋start_sec の近さ、質問文の一致度）で突き合わせてIDを引き継ぎ、
  新規の内容にだけ未使用の番号を振る。削除された番号は再利用しない。

### 2. シートに照合用の列を足す（運用）

確認シートに `start_sec` を出す。IDだけでなく秒でも突き合わせられるようにする。
（いまは `動画リンク` の `#t=` に入っているので実質持っているが、明示列にする）

### 3. 書き戻し時に照合する（安全弁）

判定をDBへ書き戻すスクリプトは、ID一致だけで書かない。
**シートの質問文とDBの質問文を比べ、一致度が低い行は書かずに止める。**
