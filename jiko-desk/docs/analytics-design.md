# 会員向けQ&Aアプリ 分析データ設計（案）

将来のQ&Aアプリで、会員の利用状況を把握して講座テーマとナレッジ改善の
優先順位を決めるためのデータ構造。**実装前の設計メモであり、未実装。**

現行の `jiko_desk.sqlite3` に以下のテーブルを足すだけで成立する。
`item_id` は既存のナレッジID（`KB-1109352698-003`）、`video_id` は既存の動画IDを
そのまま使うので、分析結果から改善対象のナレッジや講座にそのまま辿れる。

---

## 1. 記録するテーブル

### search_log — 検索

| 列 | 内容 |
|---|---|
| id | 連番 |
| ts | 日時 |
| member_hash | 会員の識別子（後述のハッシュ。生のIDは保存しない） |
| query_masked | **マスキング済み**の検索語。原文は保存しない |
| result_count | ヒット件数 |
| zero_hit | ヒット0件か |
| top_item_id | 最上位に出たナレッジID |
| channel | web / LINE など |

### view_log — ナレッジ閲覧

| 列 | 内容 |
|---|---|
| id, ts, member_hash | |
| item_id | 見られたナレッジ |
| entry | search / category / link（どこから来たか） |
| dwell_sec | 滞在秒数（読まれたかの目安） |

### feedback — 役に立った／解決しなかった

| 列 | 内容 |
|---|---|
| id, ts, member_hash, item_id | |
| verdict | helpful / not_solved |
| reason_tag | 選択式（説明が古い／内容が足りない／探していたものと違う／用語が難しい） |
| comment_masked | 自由記述。**原則使わない**。使う場合もマスキング済み・短期保持 |

### video_click — 元動画へのクリック

| 列 | 内容 |
|---|---|
| id, ts, member_hash, item_id | |
| video_id, start_sec | 飛んだ先の動画と時刻 |

### unanswered — 回答できなかった質問

| 列 | 内容 |
|---|---|
| id, ts | |
| query_masked | マスキング済みの質問 |
| cause | zero_hit（ヒット0）/ not_solved（評価が否定的） |
| status | 未対応 / ナレッジ追加済 / 講座テーマ候補 / 対応不要 |
| linked_item_id | 追加したナレッジ |
| linked_video_id | 題材にした講座 |

---

## 2. 集計（ダッシュボードの7項目に対応）

| 希望 | 集計元 |
|---|---|
| 1. 質問数・検索数 | `search_log` の件数（月次・会員数） |
| 2. よく検索されるテーマ | `query_masked` の頻度、`top_item_id` のカテゴリー別集計 |
| 3. よく閲覧されるQ&A | `view_log` の item_id 別件数と滞在秒数 |
| 4. 回答できなかった質問 | `unanswered`（zero_hit と not_solved の両方を拾う） |
| 5. 役に立った／解決しなかった | `feedback` の verdict 比率、item_id 別の満足率 |
| 6. 元動画へのクリック数 | `video_click`。閲覧数との比でクリック率も出る |
| 7. 月別の利用状況と傾向 | 上記すべてを月次で集計したビュー |

**講座テーマの決め方への接続**

- `unanswered` で件数が多いテーマ → 次の講座テーマの候補
- 満足率が低い item → ナレッジの書き直し、または該当回の撮り直し
- 動画クリック率が高い item → 文章だけでは足りない論点（解説の補強が必要）
- `video_id` 別の参照数 → どの講座回が実務で使われているか

## 3. 個人情報の扱い

検索語には患者の氏名・事故状況などが混ざる可能性がある。
**記録する前に落とす**のが原則で、「保存してから消す」運用にはしない。

### 匿名化

- **会員ID**: 生のIDは保存せず、サーバ側の秘密鍵でHMAC-SHA256したハッシュのみ。
  会員本人の特定が必要な場面（問い合わせ対応）は、会員管理側の別系統で行う。
- **検索語**: 保存前に正規表現でマスキングする。
  - 電話番号、メールアドレス、住所の番地、保険証番号、車両番号、日付の組み合わせ
  - 「〜さん」「〜様」の直前の語（氏名の可能性）
  - 日本語の氏名は完全には検出できないため、**マスキング後の文字列しか保存しない**ことを前提にする
- **自由記述**: 最もリスクが高い。原則は選択式タグのみにする。
- **少数クエリの除外**: 月の出現回数が3回未満の検索語は集計・表示の対象外にする。
  1人しか検索していない語は、それ自体が個人の特定につながりうるため。

### 保存期間

| データ | 期間 | 期間後 |
|---|---|---|
| search_log / view_log / video_click | 13か月 | 月次集計のみ残して行を削除 |
| feedback の comment_masked | 90日 | 本文のみ削除（verdictとtagは残す） |
| unanswered | 対応完了から12か月 | 削除 |
| 月次集計 | 無期限 | — |

13か月は前年同月比を見るため。削除は日次のバッチで自動実行し、手作業に依存させない。

### アクセス制限

| 役割 | 見られる範囲 |
|---|---|
| owner（MAYU） | すべて。生ログを含む |
| editor | 月次集計とナレッジ改善リストのみ。生ログは不可 |
| reviewer（講師・専門家） | 自分の確認対象のナレッジのみ。利用ログは一切不可 |

- ダッシュボードはログイン必須
- DBファイルはアプリ実行ユーザーのみ読み書き可（VPS上で 600）
- バックアップは暗号化して保管

---

## 4. 実装時の注意

- 記録はアプリ側で行う。このナレッジ生成パイプラインは記録に関与しない
- `item_id` は再生成で変わりうるため、ログ側は item_id に加えて
  **質問文のハッシュ**も持っておくと、ナレッジを作り直しても追跡できる
- 「よく検索される＝重要」は、ナレッジの並び順にも使える。
  ただし検索されない＝不要ではない（そもそも存在を知られていない可能性）
