# Make側の変更点と、投稿先を増やす話

## 1. 既存シナリオの変更点：ほぼゼロ

このBotは**シートに1行書くだけ**で、投稿の実行はしない。
既存のMakeシナリオ（投稿日 == 今日 → Instagram + Googleに投稿）はそのまま動く。

確認しておくべき点だけ:

| 確認項目 | 理由 |
|---|---|
| 行の絞り込みが**日付ベース**になっているか | Botは日付順を保つため行を挿入する。行番号固定だとずれる |
| C列のURLをそのまま `image_url` に渡しているか | ドメインが `postimg.cc` 等から `res.cloudinary.com` に変わるだけ |
| 投稿後にD列へ書き込んでいるか | Botは新規行のD列を空にする。二重投稿防止はMake側の責務 |

URLのドメインが変わるだけなので、**URL決め打ちのフィルタが無ければ変更不要**。

## 2. 一気に投稿できる先

前提として、**画像が公開URLで用意されている**ことが条件を満たす鍵になる。
このBotがCloudinaryの公開URLを作るので、投稿先を増やすのは
「同じ行を読むモジュールを足す」だけになる。

### 追加しやすい順

#### ① Facebookページ ★最優先
- Instagram Business アカウントは必ずFacebookページと連携しているので、**認証が既に通っている**
- Meta の Graph API で画像URLを渡して投稿できる
- 追加コスト実質ゼロ。やらない理由がない

#### ② Threads
- 同じMetaアカウント。Threads API（2024年公開）はInstagramと同じ
  「コンテナ作成 → 公開」の2段階方式で、画像も公開URL指定
- 整骨院の客層とThreadsの客層は重なりが薄いかもしれないが、コストが低い

#### ③ LINE公式アカウント配信 ★効果は最大
- 既存の来院患者に直接届くので、**反応率はInstagramより圧倒的に高い**はず
- Messaging API の broadcast で画像メッセージを送れる。画像はHTTPSの公開URL指定
- **注意: 配信すると料金プランのメッセージ通数を消費する**。
  友だち1,000人に月8回配信すれば8,000通。フリープランでは足りない
- 全投稿を流すのではなく、「休診のお知らせ」「キャンペーン」だけ選別して流すのが現実的
  → シートにH列「LINE配信する」チェックを足して、Make側で絞る

#### ④ X（旧Twitter）
- 投稿自体は技術的に可能
- **ただしAPIの無料枠の条件が頻繁に変わっており、現時点の上限は要確認**。
  有料プランが必要になる可能性がある（※ここは私の情報が古い可能性が高いので、
  実装前に必ず現在の料金ページを確認してください）

#### ⑤ WordPress（自院サイトのブログ）
- サイトがWordPressなら、同じ本文をブログ記事として自動投稿できる
- SNSの投稿は流れて消えるが、ブログはSEO資産として残る
- 「低気圧 頭痛 伏見区」のような検索流入を狙えるので、**中長期では一番効く**可能性がある

### 現実的に難しい / 不可

| 投稿先 | 状況 |
|---|---|
| note | 公開APIが存在しない。自動投稿は不可 |
| TikTok / YouTube | 動画前提。画像1枚の投稿は実質対象外 |
| Facebookグループ | 投稿APIが廃止済み |
| Instagramストーリーズ | 技術的には可能だが別エンドポイント。24時間で消えるため運用設計が別物 |

## 3. 先に直すべき構造的な問題

投稿先を増やす前に、これを直さないと増やすほど品質が落ちる。

**現状、B列の1つのテキストをInstagramとGoogleの両方に流している。**
しかしB列の中身はInstagram専用になっている:

```
ご予約やお問い合わせは
プロフィールのリンクからどうぞ      ← Googleに「プロフィールのリンク」は存在しない
@itukisinkyu_staff                 ← Instagramのハンドル名
#低気圧 #梅雨 #頭痛 #めまい #自律神経  ← Googleでハッシュタグは機能しない
```

つまり**Googleビジネスプロフィール側の投稿は、意味不明な文章が末尾についた状態で公開されている**。
加えてGoogleの投稿は本文が長すぎると途中で折りたたまれるため、
2,000字近い本文をそのまま流すのは形式としても合っていない。

### 対策：列を分けて、Make側で連結する

| 列 | 内容 |
|---|---|
| B | 本文（共通・プラットフォーム固有の表現を含めない） |
| E | Instagram用フッター（ハッシュタグ + プロフィール誘導） |
| F | Google用フッター（電話番号 + 予約リンク。ハッシュタグなし） |
| G | Facebook / Threads用フッター |
| H | LINE配信する（チェック） |

Make側では各モジュールで `B列 + 該当フッター列` を連結するだけ。
フッターは毎回同じ文面なので、E〜G列は数式で一括埋めできる。

Googleは短い方が読まれるため、本文も要約したい場合は
既存のGemini API（No.1 献立AIで使用中）で
「この本文を300字に要約してGoogleビジネスプロフィール用にする」処理を挟める。
これは必要になった段階で足せばよい。

---

## 4. 推奨する進め方

1. **今回のBotを動かす**（画像アップロードの手間を消す）← 最優先
2. **フッター列を分ける**（Google側の投稿品質を直す）
3. **Facebookページを追加**（コストゼロ）
4. **LINE配信を選別方式で追加**（反応率が最も高い）
5. WordPress / Threads / X は余力に応じて

2を飛ばして3〜5に進むと、おかしな文章が配信される先が増えるだけになる。
